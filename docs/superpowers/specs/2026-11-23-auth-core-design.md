# Auth core (step 3a) design

November 23, 2026. Status: approved. Step 3, part a, of `docs/superpowers/roadmaps/2026-11-23-better-auth-roadmap.md`.

## Intent

Put Better Auth inside the API as `authentication.md` specifies: invite-only sign-up, passkey, password with a verified email, 2FA, families as organizations. Step 3 is split in two PRs. This one (3a) delivers the tables, the configuration, the Nest integration, invite-only sign-up and the seed. 3b adds `@RequirePermission`, the 2FA rule, `GET /me`, `{ code, params }` errors and the remaining security tests (viewer can't upload, other family inaccessible, `creatorRole`, one role per member).

## Scope

**Goals (3a):** Better Auth tables as our migration, in snake_case with UUIDv7 IDs; `createAuth` with only the organization, passkey, twoFactor and bearer plugins; `/api/auth/*` mounted with a global guard; the `user.create.before` hook; a `Mailer` interface with a logging dev implementation; `pnpm db:seed` for the first owner and family; integration tests on a real Postgres.

**Non-goals:** everything listed for 3b; real email (step 4); web screens (step 6).

## Approaches (naming of Better Auth columns)

| | Approach | Trade-off |
| --- | --- | --- |
| A | Keep Better Auth's camelCase names | Minimal config; `CamelCasePlugin` mangles them in our queries, two naming styles in one database |
| **B (chosen)** | Map every model and field to snake_case with `modelName` / `fields`, computed from Better Auth's own table list | Consistent database; a field added by a Better Auth update without mapping fails the schema check, not silently |
| C | Give Better Auth our Kysely with `CamelCasePlugin` | Fewest lines; undocumented, and Better Auth's schema validation introspects without plugins, so it would have to be turned off |

`database.casing: "snake"` exists in the 1.7.27 types but does nothing: the generated SQL is identical with `"camel"` and `"snake"`, and no code in `better-auth`, `@better-auth/core`, `@better-auth/kysely-adapter` or the `auth` CLI reads it (checked November 23, 2026). **When a Better Auth release makes `casing` work, replace the computed mapping with it.** The mapping lives in one function so that this is a one-place change.

## Design

- **Dependencies** (exact): `better-auth` 1.7.27 (catalog), `@better-auth/passkey` 1.7.27, `@thallesp/nestjs-better-auth` 2.8.0; dev: `auth` 1.7.27 (the Better Auth CLI; `@better-auth/cli` stopped at 1.4).
- **Location:** `apps/api/src/modules/identity/`. `createAuth(db, env, mailer)` builds the config from the `authentication.md` skeleton: email + password with `requireEmailVerification`, `minPasswordLength: 12`, sessions 30 days / extended daily, `cookieCache` off, rate limit in the database, `telemetry: { enabled: false }`, `user.locale` / `user.uiSize` and `invitation.locale` / `invitation.uiSize`, `allowUserToCreateOrganization: false`, `ac` and `roles` from `@swarm-keeper/permissions`.
- **Database:** Better Auth gets our Kysely instance without plugins (`db.withoutPlugins()`): same pool, no camelCase conversion, because Better Auth maps names itself.
- **IDs:** `generateId: "uuid"`, so Postgres generates IDs; our migration sets `default uuidv7()` on every `id` column.
- **Migration:** generated by the Better Auth CLI (or its `getMigrations` API) from the full config, adapted to `uuidv7()`, committed as a Kysely migration. `schema.ts` regenerated.
- **Nest:** `AuthModule.forRootAsync` with the `DATABASE` token; Nest's body parser off as the wrapper requires; `/api/auth/*`; global guard; `@AllowAnonymous()` on `/health`.
- **Invite-only sign-up:** `user.create.before` rejects a sign-up without a pending, unexpired invitation for that email and the token from the request (`INVITE_REQUIRED`); with one, it sets `emailVerified: true`, `locale` and `uiSize` from the invitation. Right after creation the person becomes a member with the invitation's role and the invitation is marked accepted. `requireEmailVerificationOnInvitation` stays on, so an unverified account can't accept an invitation.
- **Mailer:** `Mailer` interface (`invitation`, `verifyEmail`, `resetPassword`); the dev implementation logs the link.
- **Seed:** `pnpm db:seed` creates the first owner (verified email, password) and their family from env (`SEED_OWNER_EMAIL`, `SEED_OWNER_PASSWORD`, `SEED_FAMILY_NAME`); a second run changes nothing.
- **Env:** `BETTER_AUTH_SECRET` (required in production, dev default otherwise), `BETTER_AUTH_URL` (dev: the web origin `http://localhost:4200`), `PASSKEY_RP_ID` (dev: `localhost`), in `.env.example`.
- **Tests (real Postgres, never skipped):** no pending Better Auth migrations against the migrated test database and no camelCase identifiers in its schema; IDs are UUIDv7; sign-up without an invitation is rejected; sign-up with an invitation gives a verified email and membership with the invited role; an unverified account can't accept an invitation; anonymous `/health` works and a protected route answers 401.
- **Docs:** `authentication.md` (the CLI is `auth`; snake_case mapping and the `casing` note); roadmap (step 3 split into 3a and 3b); `CLAUDE.md` (`db:seed`, auth env).

## Builder's calls

- How the invitation token reaches the hook (request body field or header), checked against 1.7.27.
- How membership is created after sign-up (`user.create.after` with a server-side `addMember`, or Better Auth's accept flow), as long as it happens in the same request.
- How the migration is produced (CLI with our config, or `getMigrations().compileMigrations()`), as long as the result is a committed Kysely migration.
