# Web sign-in and invitation (step 6a) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An invitee joins a family from the emailed link with a passkey (or a password), an existing member accepts a second family, and everyone signs in at `/login`, in English or Russian, proven end to end by Playwright.

**Architecture:**
- **API (`apps/api/src/modules/identity`):** an anonymous `GET /api/v1/invitations/:id`, plus passkey-first sign-up through Better Auth's passkey plugin (`requireSession: false`, `resolveUser`, `afterVerification`).
- **Web:**
  - `libs/web/core` gets the auth client, `AuthService`, the guards, `*appCan` and the interceptor;
  - a new `libs/web/features/auth` holds `/login`, `/invite/:token`, `/reset-password` and the signed-in placeholder `/`.
- **End to end:** a new `apps/web-e2e` package runs Playwright against the real API and the web dev server.

**Tech Stack:**
- Better Auth 1.7.27: core, the passkey, twoFactor and organization plugins and their clients.
- NestJS 12, Kysely.
- Angular 22.3: Signal Forms, Material 22.3, Transloco 8.4.
- Vitest 5, Playwright (pinned at install; Chromium with a CDP virtual authenticator).

**Spec:** `docs/superpowers/specs/2026-11-24-auth-web-design.md`. Mockups: `docs/design/mockups/auth/login.html` (layout B) and `invite.html`.

## Global Constraints

- **Error codes** (`{ code, params }`): `INVITATION_NOT_FOUND` (404, the same body for unknown, malformed, expired, accepted and canceled), `NAME_REQUIRED` (400), `INVITE_REQUIRED` (400, existing), `TWO_FACTOR_REQUIRED` (403, existing).
- **Passkey sign-up never creates a `credential` account.** The user is created `emailVerified: true`, with `locale` and `uiSize` from the visitor's last choice (`en` | `ru`, otherwise `invitation.locale`, otherwise `en`).
- **Locale** sent by the client:
  - in the passkey `context` JSON `{ invitation, name, locale }`;
  - in the password sign-up body as `locale`, overriding the invitation's when it is `en` or `ru`.
- **Password minimum is 12 characters** (`minPasswordLength` already 12).
- **Routes:** `/login`, `/invite/:token`, `/reset-password`, `/`.
  - `guestGuard` on `/login` and `/reset-password`;
  - `authGuard` on `/`;
  - `/invite/:token` has no guard.
- **Interceptor:** 401 on `/api/v1/*`, except `GET /api/v1/me`, → `/login?returnUrl=…`. 403 `TWO_FACTOR_REQUIRED` → `/settings/security`.
- **Frontend rules:**
  - standalone components, OnPush, signals, Signal Forms;
  - tokens only, no fixed widths, no literal text in templates;
  - translations in scope `auth` (`apps/web/src/i18n/auth/{en,ru}.json`) and `errors.auth.*`, in the glossary tone (formal «вы», no exclamation marks).
- **Sheriff:**
  - `feature:auth` may use `web:core`, `web:ui` and shared libraries only;
  - the API module adds no new dependency beyond the pinned `better-auth`;
  - `apps/web-e2e` is not a Sheriff module (no `src/index.ts` entry); add it to the ESLint ignores if needed.
- Conventional Commits with the Claude co-author line. Option names are checked against the installed Better Auth 1.7.27.

## Review Focus

1. **Double submit on "Create account with passkey":** a second click, or a retry after a cancelled ceremony, must not create two users or two memberships. The invitation is re-checked as pending inside `afterVerification`'s transaction. Test in Task 2: two verifications of the same invitation produce one user.
2. **Invitation email in a different case** (`Valya@Example.org`): sign-up must work, and the lookup's `hasAccount` must see an existing `valya@example.org`. Tests in Tasks 1 and 2.
3. **A `returnUrl` that points off-site** (`//evil.example`, `https://evil.example`): after sign-in, only same-origin paths are followed; anything else goes to `/`. Test in Task 3.
4. **The invitation expires while the page is open:** the passkey or password submit answers `INVITE_REQUIRED`, and the page shows the expired state, not a raw error. Test in Task 5.
5. **A signed-in user opens their own invitation link after accepting it:** the lookup answers 404, and the page shows "no longer works" with a way to `/`. It must never loop through `/login`. Test in Task 5.

**Files:**

  - `docs/architecture/authentication.md` ("How a new member joins", step 3: passkey-first is real in 1.7.27; the passkey path and the password path)

**Interfaces:**
- `passkeySignUp(db: Database): PasskeyRegistrationOptions`. It returns `{ requireSession: false, resolveUser, afterVerification }`:
  - **`resolveUser({ ctx, context })`.**
    - With a session, it returns the session user, so ordinary "add a passkey" keeps working.
    - Without one, it parses `context` as `{ invitation: string; name: string; locale?: string }`. Invalid JSON or a missing invitation → `APIError('BAD_REQUEST', { code: 'INVITE_REQUIRED' })`; an empty trimmed name → `NAME_REQUIRED`.
    - It requires a pending, unexpired invitation (`findPendingInvitationById`) whose email has no user yet (case-insensitive); otherwise `INVITE_REQUIRED`.
    - It returns `{ id: uuidv7(), name: invitation.email, displayName: name.trim() }`. Take `uuidv7` from Postgres with `select uuidv7()`, so no new dependency is needed.
  - **`afterVerification({ ctx, user, context })`.**
    - Without a session only. It re-runs the same checks with a row lock (`for update`) on the invitation, through the current adapter or transaction (`getCurrentAdapter` from `@better-auth/core/context`).
    - It creates the user through `ctx.context.internalAdapter.createUser({ id: user.id, email, name, emailVerified: true, locale, uiSize })`, so the hooks run.
    - It inserts the `member` row and sets the invitation to `accepted` through the same adapter.
    - It returns `{ userId: user.id }`.
  - **How the invite-only before-hook recognises the passkey path:** a request-scoped marker. `afterVerification` sets `ctx.context.passkeySignUp = { invitationId, locale }` before `createUser`; the hook reads it alongside `inviteToken`. The after-hook returns early when the marker is present. Record the mechanism as a ruling if the context object can't carry it.
- **Test helper:** `registerWithPasskey(app, { invitation, name, locale }, options?)` in `testing-webauthn.ts` runs the full ceremony:
  - `GET /api/auth/passkey/generate-register-options?context=…` (keep the cookie);
  - make the credential;
  - `POST /api/auth/passkey/verify-registration` with `{ response, createSession: true }`.

  It returns the supertest responses and the session token.
